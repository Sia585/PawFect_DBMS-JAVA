# Backup and restore design (planned, not yet implemented)

Status: design note for a later milestone. Nothing here is built yet. It records how pet photographs fit, so the
backup/restore feature does not have to change the storage model.

## What a backup contains

Pawfect's data lives in two places that must be saved together:

| Part | Where | Notes |
|---|---|---|
| Database | `backend/pawfect.db` | pets, care records, weights, revision counter. `pet.photo_file` holds only a generated file name. |
| Photographs | `backend/photos/<32 hex>.jpg` | One file per pet at most. Names are random and never reused. |

A backup is one folder or zip with:

```
pawfect-backup-YYYYMMDD-HHMMSS/
  pawfect.db          consistent snapshot made with VACUUM INTO (safe while the app runs)
  photos/             only the files named by pet.photo_file in that snapshot
  manifest.json       { app version, schema version (PRAGMA user_version), created at,
                        counts (pets, records, weights, photos), SHA-256 of every file }
```

Taking the snapshot first and then copying exactly the photos it references keeps the two consistent even if the
app is used during the backup. Photos added or replaced afterwards are simply not in that backup.

## Restore

1. Read `manifest.json`; refuse a schema version newer than the running code (the existing `Migrator` rule).
2. Verify every checksum, run `PRAGMA integrity_check` and `PRAGMA foreign_key_check` on the snapshot.
3. Restore into a new database file and a new photos folder, then swap them in. The current database is kept as a
   pre-restore backup (the same mechanism that already protects schema migrations). The `revision` counter is bumped
   past any open browser tab so those tabs get the normal "updated elsewhere" dialog instead of overwriting the restore.
4. A referenced photo that is missing or fails its checksum is not an error: the pet keeps its row and the page shows
   the emoji (the browser already falls back when a photo cannot load). The restore report lists such pets.
5. Files in `photos/` that no pet references are never restored.

## Rules that make this safe

- Photo file names are generated by the server and validated against `[0-9a-f]{32}\.jpg`, so a bundle cannot smuggle
  a path (`../`) into the restore.
- Restored photos are re-validated with the same `ImageProcessor` as uploads (real JPEG/PNG, size limits) before use.
- Restore never writes outside `backend/` and never contacts an external service.
- Backups and photos are personal data: both stay out of git (`backups/`, `photos/`, `*.db` are already ignored).
